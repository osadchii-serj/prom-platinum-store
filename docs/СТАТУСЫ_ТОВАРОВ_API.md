# PROM — жизненный цикл статусов товаров через API

**Статус:** контракт документирован; отдельные переходы проверены на тестовой карточке; массовые операции не испытаны.

## Источник контракта

Официальная спецификация Prom.ua:

- `https://public-api.docs.prom.ua/documentation/Products/paths/PostProduct.yaml`
- `https://public-api.docs.prom.ua/documentation/Products/schemas/PostProductRequestBody.yaml`
- `https://public-api.docs.prom.ua/documentation/Products/responses/PostProductResponse.yaml`

`POST /products/edit` принимает JSON-массив объектов; обязательное поле `id` (integer). `status` допускает `on_display`, `draft`, `deleted`, `not_on_display`. Ответ содержит `processed_ids` и `errors`. HTTP 200 недостаточен: необходимо проверить, что обработан ожидаемый ID и ошибок нет.

## Подтверждённые испытания (23.10.2026)

Карточка ID `3243922294`, SKU `PROM-TEST-20261022-001`:

| Переход | Проверка |
| --- | --- |
| `draft → deleted` | POST 200, ID обработан, карточка в удалённых кабинета |
| `not_on_display → deleted` | POST 200, ID обработан, карточка в удалённых кабинета |
| `deleted → not_on_display` | POST 200, ID обработан, GET 200, совпали ID/SKU/status, кабинет подтверждает |
| `deleted → not_on_display` через кабинет | Восстановлено вручную, GET 200, статус `not_on_display` |
| `on_display ↔ draft`, `draft ↔ not_on_display` | Ранее проверены отдельными испытаниями |

GET `/products/3243922294` после удаления возвращал HTTP 404; **это не доказательство безвозвратного уничтожения**. При восстановлении карточка снова доступна через GET с тем же ID и SKU.

## Ограничения и безопасность

- Проверенные переходы на одном товаре **не доказывают** универсальность для разновидностей, групп и массовых операций.
- `deleted → draft`, `deleted → on_display`, `on_display → deleted` не испытаны и не разрешены новым модулем.
- Для обычной карточки перед POST проверить ID/SKU/исходный статус через GET; для удалённой карточки GET 404 не подтверждает идентичность — нужны сохранённый снимок и подтверждение через кабинет/журнал.
- Для каждой записи: предпросмотр → подтверждение → один POST → проверка `processed_ids/errors` → независимый GET/кабинет → журнал результата.
- При тайм-ауте или ошибке после POST **не повторять автоматически**. Установить фактическое состояние отдельно.
- Токены не печатать и не сохранять в журнале.
- В `src/prom/api/статусы_товаров.py` выделены проверки и один POST, но пока нет оркестрации полного жизненного цикла, долговременного журнала и массового выполнения. Это фундамент, а не готовый массовый инструмент.
