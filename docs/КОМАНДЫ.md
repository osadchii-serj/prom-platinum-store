## 9. Проверенные контракты и ограничения

- `GET /products/{id}` возвращает `status`, `presence` и другие свойства.
- `POST /products/edit` принимает массив объектов; для испытанных переходов достаточно `id` и `status`.
- Документированные значения `status`: `on_display`, `draft`, `not_on_display`, `deleted`. **Переходы в `deleted` не испытывались.**
- Документированные значения `presence`: `available`, `not_available`, `order`.
- Проверенные переходы: `on_display → draft`, `draft → not_on_display`, `not_on_display → draft`.
- Создание непосредственно в `draft` через импорт **не подтверждено**. Импорт тестового товара привёл к `on_display`.
- Отдельные значения `status` и `presence` не следует смешивать.
- Счётчики каталога API и кабинета различаются; причина ещё не установлена.

## 10. Правила безопасности

1. По умолчанию только предпросмотр; реальные записи — исключительно с `--отправить` и точным подтверждением.
2. Перед POST сверять ID, SKU и исходный статус; после POST проверять `processed_ids`, `errors` и итоговый GET.
3. Не повторять POST автоматически после HTTP-ошибки, таймаута или неопределённого результата.
4. Не выводить API-токены, `.env`, персональные данные и непроверенные тела HTTP-ответов в журналы.
5. Не применять экспериментальные команды массово; не менять статус `deleted` без отдельного сценария восстановления.
6. Обновлять этот документ при изменении имён скриптов и аргументов команд.

## 15. Этап 2.5 — полное чтение каталога и Rich

Установка из корня проекта:

```bash
unzip -l ~/Загрузки/PROM_этап2_5_чтение_каталога_Rich.zip

# После просмотра:
cp /tmp/prom_команды_2_5.md docs/КОМАНДЫ.md
uv run ruff check .
uv run mypy .
uv run pytest -q
git diff --check
```

API-модуль `prom.сценарии.чтение_каталога` предоставляет
`прочитать_каталог(соединение)`, `получить_стабильный_снимок()`,
`показать_чтение(итог)`. Первый проход читает GET `/products/list`
постранично по `last_id`, контролирует ID, дубли и завершение. Второй
проход сравнивает нормализованные записи. Используется токен **чтения**.
При неполной пагинации функция выбрасывает исключение; при расхождении
двух проходов `снимок.полный=False`. Это **не транзакционный снимок**:
изменения между запросами теоретически могут остаться незамеченными.
Никаких POST или операций изменения товаров нет.

Пример только чтения при наличии `PROM_API_TOKEN_READ`:

```bash
uv run python -c 'from prom.сценарии.чтение_каталога import получить_стабильный_снимок, показать_чтение; показать_чтение(получить_стабильный_снимок())'
```

Сверку до/после импорта выполняют отдельно, сохраняя снимок «до» до
начала импорта. Сам этап 2.5 ещё не связывает новые ID с конкретным импортом.



Повторное сохранение того же этапа заблокировано (файл не
перезаписывается). Снимок сохраняется с SHA-256 и проверяется при чтении.

злоумышленника, способного изменить и JSON, и его хеш**.
Два прохода GET не являются транзакционным снимком.

Новые ID — кандидаты, а не доказательство происхождения из нашего
импорта. Никаких автоматических изменений статусов товаров.


Путь к журналу — пример: указывать фактический файл, созданный

журнал импорта отсутствует: **не создавать фиктивный журнал ради проверки**.

Проверяется: совпадение ключей, целостность обоих снимков, порядок
времени `до < обновление журнала < после`, итоговый статус `SUCCESS`,
завершённое состояние, числовой ID импорта и различия ID карточек.
При отсутствии данных проверка завершается ошибкой или предупреждением.

**Ограничения:** время обновления журнала не является временем
отправки POST; этот этап не доказывает, что импорт был единственной
причиной изменений. Счётчики API не сопоставляются с реальными
изменениями карточек; повторный POST по-прежнему заблокирован
механизмами предыдущих этапов. Изменение статусов не разрешено.
